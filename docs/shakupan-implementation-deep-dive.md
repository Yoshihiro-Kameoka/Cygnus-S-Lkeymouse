## 0. 先に結論（どう思うか）

**「マルチ OS を日常運用する人向け」としては、三者の中でいちばんよく考えられている**、という認識でよい。

ただし正確にはこう分けた方がフェアです。

| 観点 | 評価 |
|---|---|
| 配布用の汎用ベース | **sayu の方が上手**（単純・説明しやすい・COROPIT はコメントで分岐） |
| 作り手自身の業務・複数端末運用 | **shakupan がいちばん深い** |
| Cygnus 現状 | ハードウェア近いが、OS 運用設計はほぼ未着手（旧世代トラボ実装） |

shakupan 実装の強みは「キーが好き」ではなく、**接続先・OS 差分・ポインティング・スクロールを一つの操作モデルに統合している**点にある。  
ZMK 本体に「BT プロファイル変更で自動レイヤー切替」がまだ無い中で、マクロで実用レベルまで落としているのは、コミュニティ的にも筋が良い（本人の解説: [Zenn 記事](https://zenn.dev/shakupan/articles/261ce435251607)）。

弱点もある（後述）。神実装というより、**目的が明確なプロダクト設定**に近い。

## 1. sayu と何が「特有」か（差分の地図）

sayu は「みんなの出発点」。shakupan はそれを fork して、**自分の手に馴染む運用系**を積み上げている。

| 領域 | sayu | shakupan 特有 |
|---|---|---|
| キーマップ思想 | 単一 OS 前提の実用配列 | **Win/Mac 二系統の木構造** |
| BT 切替 | `BT_SEL` 単体 | **BT 切替 + ベースレイヤー強制同期マクロ** |
| スクロール層 | レイヤー 3 の 1 本 | **OS 別 6/7、マウス層から `&mo` で入る** |
| スクロール倍率 | `1/5` 前後 | **`1/20`（精密優先）** |
| 軸反転 | コメントアウト（COROPIT は手順書） | **invert-x/y 有効化済み** |
| エンコーダ | steps 24 / 単純 sensor-bindings | **steps 96 + 専用 listener + 左 half のスレッド調整** |
| USB | 既定 | **HID poll 1ms** |
| マウス加速 | 既定寄り | **`&msc` 加速実質オフ（即応）** |
| 独自マクロ | 少なめ | screenshot / henkan / BT0 / BT1 など |
| upstream | 公式本体 | diverged（個人最適化が先行） |

「革命的」に見える中核は、ほぼ **BT×レイヤー同期 + OS 別レイヤーの縦割り** である。

## 2. 中核思想: 「接続先 = OS プロファイル」

### 2.1 問題設定

無線分割キーボードでは、1 台の鍵盤が複数 PC / タブレットに繋がる。  
OS ごとに違うのは主に:

- 修飾キーの主役（Win: Ctrl、Mac/iOS: Gui）
- スクショやウィンドウ操作のコード
- たまに IME・メディア

ZMK は「今どの OS か」を自動では知らない。代わりに使えるのが **BT プロファイル番号**。

### 2.2 shakupan の解

> 接続先を切り替える操作そのものに、OS 用ベースレイヤーの切替を埋め込む

Zenn での本人の手順も同じ型:

1. 全デフォルトレイヤーを OFF  
2. 少し待つ  
3. `BT_SEL n`  
4. 対応レイヤーを ON  

実装（要約）:

```text
BT0: tog_off(0), tog_off(1) → wait → BT_SEL 0 → wait → tog_on(0)   # Win
BT1: tog_off(0), tog_off(1) → wait → BT_SEL 1 → wait → tog_on(1)   # Mac
```

### 2.3 なぜ `&to` ではなく `tog_on` / `tog_off` か

ここが「よく考えている」ポイントの一つ。

- `&to N` はレイヤー遷移の意味合いが強く、スタック運用と噛み合いにくい場面がある
- **ベースを「トグルで載せるレイヤー」として扱い**、その上に `&mo` / `&lt` の一時レイヤーを重ねる
- 切替時に両方 OFF してから片方 ON にすることで、**Win と Mac のベースが同時に残る事故**を防ぐ

`wait 200/500` も雑ではなく、BLE 切替の立ち上がりを待ってからレイヤーを確定させる実務的バッファ。

### 2.4 公式機能ではない、という位置づけ

ZMK 本体には、今も「プロファイル変更で自動レイヤー」の本機能は無い（議論はある）。  
shakupan 方式は **公式未実装を、キーマップマクロで先に体験として完成させている**。

注意（本人も言及）:

- 電源投入直後など、接続先とレイヤーがずれることがある → もう一度切替マクロを押す
- BT2 以降（現状キーにある素の `BT_SEL 2..4`）は、**レイヤー同期マクロが付いていない**

つまり「完全自動」ではなく、**切替操作を正しい単一入口に揃えた設計**。

## 3. レイヤーの木構造（いちばんの設計資産）

現状の並び（keymap 上の定義順）:

| Index | 名前 | 役割 |
|---|---|---|
| 0 | `win_layer` | Windows ベース |
| 1 | `mac_layer` | Mac ベース |
| 2 | `num_win` | Win 数字・記号 |
| 3 | `num_mac` | Mac 数字・記号 |
| 4 | `mouse_win` | Win マウス + ショートカット |
| 5 | `mouse_mac` | Mac マウス + ショートカット |
| 6 | `scroll_win` | Win 時のボールスクロール層 |
| 7 | `scroll_mac` | Mac 時のボールスクロール層 |
| 8 | `function_win` | 追加（薄い） |
| 9 | `function_mac` | 追加（薄い） |
| 10 | `ble_win` | BT / bootloader（Win 経路） |
| 11 | `ble_mac` | BT / bootloader（Mac 経路） |

### 3.1 アクセス経路が OS で対になる

ベースから見える入口（要約）:

| 操作（イメージ） | Win ベース | Mac ベース |
|---|---|---|
| 数字層 | `&lt 2 ...` | `&lt 3 ...` |
| マウス層 | `&lt 4 SPACE` | `&lt 5 SPACE` |
| スクロール層 | `&lt 6 MINUS` | `&lt 7 MINUS` |
| BLE 層 | `&lt 10 SLASH` | `&lt 11 SLASH` |

親指・端キーの「役割」は同じで、**飛び先レイヤー番号だけ OS でずらす**。  
これが「OS を意識しない」体感の正体。ユーザーは同じ場所を押す。キーボードが Win/Mac を知っている。

### 3.2 マウス層 → スクロール層のつなぎ

- `mouse_win` 内に `&mo 6`（scroll_win）
- `mouse_mac` 内に `&mo 7`（scroll_mac）

ポインティング作業中にスクロールへ入っても **OS コンテキストが切れない**。  
sayu の「レイヤー 3 がスクロール兼カーソル」より、役割分割が明確。

### 3.3 overlay 側の scroller も対で受ける

```text
scroller { layers = <6 7>; ... scaler 1 20; }
```

キーマップの scroll_win/mac と、センサ側の「いつボールをホイールにするか」が一致している。  
**キーマップだけ・ドライバだけ、の片手落ちになっていない。**

Cygnus 旧方式（`scroll-layers = <5>` をドライバに直書き）より、この分離の方が OS 増設（iOS）に耐える。

## 4. OS 差分を「どこに閉じ込めたか」

全部を二重化しているわけではない。差分が出る場所に寄せている。

### 4.1 ベースの修飾キー

- Win: 左下付近が `RCTRL` / `LEFT_WIN` / `LEFT_ALT`
- Mac: `LEFT_GUI` を前面に（Cmd 操作の主役）

文字キーそのもの（QWERTY）は共通。差分は親指・修飾・レイヤー入口。

### 4.2 マウス層のショートカット

同じ「位置」でも送出コードが変わる例:

| 意図 | Win | Mac |
|---|---|---|
| Undo 系 | `LC(Z)` など | `LG(Z)` / `LG(LS(Z))` |
| スクショ | `screenshot` マクロ（Win+Shift+S 系） | `LG(LC(LS(NUMBER_4)))` など |
| 変換っぽい操作 | `henkan` マクロ | `LC(SPACE)` など |

「マウス層に編集ショートカットを載せる」こと自体が、トラックボール機ならではの密度設計。

### 4.3 num 層

見た目の数字配列はほぼ同じで、左下修飾だけ Win/Mac 差。  
ここは二重管理コストが低い。

### 4.4 まだ薄いところ

`function_mac` に `&kp A` だけ見えるなど、**未完成・実験跡**もある。  
全部が研磨済みではなく、優先度の高い経路（base / mouse / scroll / ble）から固めている印象。

## 5. ポインティング周りの思想

### 5.1 新世代スタックは sayu と同じ土台

- `badjeff` PMW3610
- `cpi = <600>`
- input listener + processors

shakupan 固有なのは土台そのものより **チューニングと OS 統合**。

### 5.2 スクロールを遅くした理由（推測含む）

`zip_scroll_scaler 1 20` は sayu よりかなり鈍い。

トラックボールスクロールは、速すぎると:

- ドキュメントで飛びやすい
- 精密 UI（表計算・設計・コード）でストレス

「カーソルは 600 で普通に動かし、ボールスクロールは精密器具にする」という役割分担に読める。  
速さ自慢より、**用途分離**が上手い。

### 5.3 `&msc` の加速を殺している

```text
delay-ms = 0
time-to-max-speed-ms = 0
acceleration-exponent = 0
```

エンコーダやホイール相当の加速を捨て、入力に対して線形に近くする。  
予測不能な加速より、指の移動と結果を一致させる方向。

### 5.4 COROPIT invert を本番値にしている

配布ベースならコメントアウトが親切。  
shakupan リポは **自分の手元ハードウェア前提**なので、最初から invert ON。  
「公式」ではなく「作者常用ブランチ」であることの現れ。

## 6. エンコーダ（左手）の作り込み

sayu 比で明確に重い。

| 項目 | sayu | shakupan |
|---|---|---|
| steps | 24 | **96** |
| triggers-per-rotation | 10 | **24** |
| 左 conf | GLOBAL_THREAD | **OWN_THREAD + priority/stack** |
| 追加経路 | sensor-bindings 中心 | **`encoder_left_listener` で scroll 変換 + 1/4** |

意図:

- 分解能を上げて滑らかにする
- 左 half でエンコーダ処理を専用スレッド化（取りこぼし低減）
- listener 経由でもスクロールに落とす

ここは「よく考えている」一方、**複雑度と効果のコスパは実機依存**。  
Cygnus 移植時は、最初から 96 を真似せず、まず BT×OS を固めて後回しでもよい。

## 7. その他の実務マクロ

### BT0 / BT1

前述。運用の単一入口。

### screenshot / henkan

OS 固有の「よく使うがキーが遠い」操作を、マウス層など親指圏に回収。  
トラックボール機はホームポジションを崩したくないので、この手のマクロ価値が高い。

### combo

- 親指付近コンボで ESC / レイヤー
- S+D 相当で Tab

小型配列でキー不足を補う定石を、OS 二系統の上でも維持。

### USB 1000Hz

有線接続時だけ効く。デスクに挿して使う場面の応答を詰める、作者用途の最適化。

## 8. 設計上の上手い点（要約）

1. **問題の置き方**が正しい（OS 判定ではなく BT を代理指標に使う）  
2. **切替の入口を一つに束ねる**（BT とレイヤーを同時変更）  
3. **レイヤーを OS で対にしつつ、ユーザーの指の役割は共通**  
4. **スクロールをキーマップと overlay の両方で OS 対応**  
5. **ポインティングは精密/通常で役割分け**（CPI と scroll scaler）  
6. 新世代 ZMK（input processors）の上に載せており、**拡張（iOS 追加）がしやすい**

これが「一番よく考えられている」と感じる正体だと思う。

---

## 9. 限界・弱み（ここも見ておく）

1. **保守コストが高い**（レイヤーが増えるほど変更が倍）  
2. upstream（sayu）から diverged しており、公式追従が手動  
3. **起動時不整合**をゼロにはできない（マクロ方式の宿命）  
4. BT2〜4 は同期マクロ未接続（iOS を足すなら BT2 マクロが必要）  
5. COROPIT 前提値が混ざる（非 COROPIT だと向きが逆）  
6. 一部レイヤーは未研磨  
7. 「全員にとって最良」ではなく **作者の業務最適化**

sayu を「教科書」、shakupan を「上級者の完成形サンプル」と見るのが扱いやすい。

## 10. Cygnus へ持ち込むときの優先順位

ロードマップと整合させるなら:

| 優先 | 持ち込むもの | 理由 |
|---|---|---|
| 高 | BT×ベースレイヤー同期（Win/Mac、次に iOS） | 体験の核 |
| 高 | OS 別 mouse/scroll の対構造 | 核を支える骨格 |
| 中 | CPI 600、scroll scaler の思想（精密スクロール） | 体感 |
| 中 | `&msc` 加速オフ | 簡単で効く |
| 低 | エンコーダ 96 + own thread + listener | 複雑、後でよい |
| 低 | USB 1000Hz | 有線派なら |
| 注意 | COROPIT invert | 実機向きを見てから |

「全部コピー」より、**§8 の 1〜4 を先に移植**するのがコスパ良い。

## 11. iOS を足すなら（shakupan 型の自然な延長）

本人の Zenn では既に Mac / Windows / iPad の表が出ている。  
今の公開 keymap は Win/Mac 中心だが、思想は最初から 3 端末を見ている。

自然な延長:

```text
BT2: 全 OS ベース OFF → BT_SEL 2 → ios_base ON
```

- base / mouse / scroll を必要最小限で三重化
- Mac に近い部分は共有し、差分だけ `ios_*`
- ble 層の `BT_SEL 2` を素の切替から `BT_IOS` マクロへ置換

Cygnus ロードマップ Phase 3 は、この延長そのもの。

---

## 12. 総合評価（再掲）

- **思想: とても良い。** 特に BT×OS レイヤー同期は、複数端末時代の ZMK 運用として第一級。  
- **実装: 実務的で深い。** ただし個人最適化であり、配布純度では sayu が上。  
- **Cygnus の参考元: shakupan を「目標アーキテクチャ」、sayu を「移行時の土台」にするのが妥当。**

「一番よく考えれた実装」という感覚は、少なくとも **本比較の三者の中では妥当**。  
世界中の ZMK 設定全体で絶対最良、とまでは言わないが、**学ぶ価値が最も高い参照実装**ではある。
